# 02 · Deploy path — PC to cvx-hel1

Principle: **the server is rebuilt from the repository, never updated by hand.** Code travels by
git. Data is regenerated by seed. Configuration is one `.env` per host, written once, never copied.

## What moves and how

| Thing | Transport | Never |
|---|---|---|
| Code, migrations, seed scripts, brand config, logo | `git push` → `git pull` on the server | copy scripts, zip uploads, file sync |
| Database contents | `npm run reset` on the server (migrate → seeds → verify) | `pg_dump` from the PC, volume copies |
| Uploaded demo documents (DMS) | committed under `seed/documents/` as synthetic fixtures | copying `DATA_ROOT` |
| Secrets | typed once into the server's `.env`, vault entry `vault: Avianca/avademo-env` | `.env` in git, `.env` over scp |
| Image | built ON the server from the pulled commit, tagged `ava-demo:<sha>` | pushing images from the PC |

## Git remote (decision pending — see brain DECISIONS)

Preferred: a private remote (GitHub private repo or a Gitea on cvx-hel1) that both the PC and the
server can reach; the server pulls with a read-only deploy key. Fallback if no remote is wanted:
`git bundle create ava.bundle main` on the PC, `scp` the bundle, `git pull ava.bundle main` on the
server — still git, still a commit, still no file copies.

## Local loop (PC)

```powershell
Set-Location "C:\Avianca TMS"
docker compose -f scaffold\deploy\compose.yml up -d db pdf     # project name ava, ports 5433 / 3101
npm --prefix scaffold run migrate
npm --prefix scaffold run reset                                # config → framework → templates → synthetic → verify
npm --prefix scaffold run dev                                  # http://localhost:3100
git add -A; git commit -m "slice: <module> — <what>"; git push
```

## Server loop (cvx-hel1)

```bash
cd /opt/ava/repo && git pull --ff-only
SHA=$(git rev-parse --short HEAD)
docker build -t ava-demo:$SHA -f scaffold/Dockerfile scaffold
sed -i "s/^APP_IMAGE_PROD=.*/APP_IMAGE_PROD=ava-demo:$SHA/" scaffold/.env
docker compose -f scaffold/deploy/compose.yml -f scaffold/deploy/compose.prod.yml up -d
docker compose -f scaffold/deploy/compose.yml exec app npm run migrate   # migrations only; reseed is a separate, deliberate step
curl -s http://127.0.0.1:3100/api/health
```

Reseeding (`npm run reset`) on the server wipes and regenerates the demo population. It is run on
purpose before a demo, never as part of a deploy. The migrate-vs-deploy order follows the kit's rule:
migrate first when the new image needs the new schema; deploy first when the old image tolerates it.

## Proofs after every server deploy

1. `/api/health` reports `env: prod`, the expected release sha, `subjects: N`, `inference: <mode>`.
2. `npm run smoke` from inside the container fetches every route and every subject page.
3. `npm run verify` green, including the neutrality scan.
4. Open `https://avademo.corvanox.com` through Access and run the first three steps of the demo
   script by hand.

## Server prerequisites (one-time, Phase 4)

- cvx-hel1 has full-disk LUKS and cannot reboot unattended. Do not reboot it for Ava. If a reboot is
  ever needed, it is a separate, human-attended operation on the Corvanox project's terms.
- Create `/opt/ava/{repo,data}`, the deploy key, the `.env` from `scaffold/.env.example`, and prove
  the three ports are free (`docs/01_ISOLATION.md`) before the first `up -d`.
- Cloudflare: one ingress rule, one CNAME, one Access application — hostname-scoped, nothing else.
