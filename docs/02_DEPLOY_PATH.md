# 02 · Deploy path — PC to cvx-hel1

Revised 2026-09-15, after building the image and running the deployed shape end to end on the
workstation. Everything below has been executed; nothing in it is a plan.

Principle: **the server is rebuilt from the repository, never updated by hand.** Code travels by
git. Data is regenerated by seed — **the database is never copied**. Configuration is one `.env` per
host, written once, never copied.

## What moves and how

| Thing | Transport | Never |
|---|---|---|
| Code, migrations, seed scripts, brand config, logo | `git push` → `git pull` on the server | copy scripts, zip uploads, file sync |
| Database contents | `gen` → `reset:clean` → `seed:history` on the server | `pg_dump` from the PC, volume copies |
| Uploaded demo documents (DMS) | committed under `data/library/` as synthetic fixtures | copying `DATA_ROOT` |
| Secrets | generated into the server's `.env` by the snippet below, vault entry `vault: Avianca/avademo-env` | `.env` in git, `.env` over scp, a password on a command line |
| Image | built ON the server from the pulled commit, tagged `ava-demo:<sha>` | pushing images from the PC |

## Git remote (decision pending — see brain DECISIONS)

Preferred: a private remote (GitHub private repo or a Gitea on cvx-hel1) that both the PC and the
server can reach; the server pulls with a read-only deploy key. Fallback if no remote is wanted:
`git bundle create ava.bundle main` on the PC, `scp` the bundle, `git pull ava.bundle main` on the
server — still git, still a commit, still no file copies.

## The image

**The build context is the REPOSITORY ROOT, and the Dockerfile lives in `scaffold/deploy/`.**

```bash
docker build -f scaffold/deploy/Dockerfile -t ava-demo:$SHA .
```

Not `-f scaffold/Dockerfile scaffold`. `KIT_ROOT` in `scripts/lib/kit-seed.mjs` resolves three
levels up from `scripts/lib`, i.e. the repository root, and every seed script reads its inputs from
`<root>/data`. The container therefore mirrors the repository — `/app/scaffold` and `/app/data` —
rather than flattening the app to `/app`. Flatten it and every script looks for its data one
directory too high and says so in a way that names neither the cause nor the file.

The image contains the app, the scripts, the migrations, the YAML config, `data/library/` and the
competency-framework document. It does **not** contain generated data (programs, roster, history):
that is produced inside the container, deterministically, as part of building the instance.

## The environment file

One per host, at `scaffold/.env`, never committed. Three values are secrets and are **generated into
the file rather than typed**, so they never reach the shell history or the npm log:

```bash
cd /opt/ava/repo/scaffold
DB_PASS=$(openssl rand -hex 24)
cat > .env <<ENV
APP_IMAGE_PROD=ava-demo:REPLACED_ON_EVERY_DEPLOY
APP_ENV=prod
APP_RELEASE=REPLACED_ON_EVERY_DEPLOY
APP_BASE_URL=https://avademo.corvanox.com
TZ=America/Bogota
POSTGRES_USER=ava
POSTGRES_PASSWORD=$DB_PASS
POSTGRES_DB=ava
DATABASE_URL=postgres://ava:$DB_PASS@db:5432/ava
SESSION_SECRET=$(openssl rand -hex 32)
INTERNAL_API_TOKEN=$(openssl rand -hex 32)
AUTH_FORCE_PASSWORD_CHANGE=false
APP_PORT=3110
DB_PORT=5433
PDF_PORT=3101
DATA_ROOT=/opt/ava/data
LOG_LEVEL=info
LOG_JSON=true
ENV
chmod 600 .env
unset DB_PASS
```

Two things in there are easy to get wrong and expensive to find:

- **`DATABASE_URL` names the SERVICE `db` on 5432**, not `localhost` on the published port. Inside
  the compose network the app is a container; point it at localhost and it resolves its own
  loopback, finds nothing, and reports the database unreachable.
- **`TZ` is the OPERATOR's timezone.** A container has no timezone unless it is given one, so
  without this every server-rendered timestamp — including the time a signature was given — comes
  out in UTC while the browser beside it renders Bogotá time.

## Server loop (cvx-hel1)

```bash
cd /opt/ava/repo && git pull --ff-only
SHA=$(git rev-parse --short HEAD)
docker build -f scaffold/deploy/Dockerfile -t ava-demo:$SHA .
cd scaffold
sed -i "s/^APP_IMAGE_PROD=.*/APP_IMAGE_PROD=ava-demo:$SHA/; s/^APP_RELEASE=.*/APP_RELEASE=$SHA/" .env

C="docker compose -p ava-prod --env-file .env -f deploy/compose.yml -f deploy/compose.prod.yml"
$C up -d --wait db pdf
$C run --rm app npm run migrate        # migrations only; reseeding is a separate, deliberate step
$C up -d --wait --force-recreate app
curl -s http://127.0.0.1:3110/api/health
```

`-p ava-prod` is not decoration. The compose files declare the project name `ava`, which is also the
development stack's; without the override, compose treats the other stack's containers as members of
this project and removes them as orphans.

`--wait` is not optional either. `up -d` returns when the CONTAINER starts, not when Postgres is
ready, and a fresh volume runs initdb first; without it the first migration meets "Connection
terminated unexpectedly" and everything after it fails complaining about a missing table rather than
about the database that was not up.

## Building the instance (first deploy, and before a demo, never as part of a routine deploy)

Destructive and meant to be. It runs in **one** container invocation, because `run --rm` deletes the
container and the generated data with it.

```bash
$C run --rm app sh -c "npm run gen:programs && npm run gen:roster && npm run reset:clean && npm run seed:history"
$C run --rm app npm run user -- a.betancur instructor --fleet A320 --person "Andrea Betancur"
$C run --rm app npm run user -- <manager> training_manager --person "<their roster name>"
$C run --rm app npm run password -- admin_av
$C run --rm app npm run password -- a.betancur
$C run --rm app npm run password -- <manager>
```

`reset:clean`, never `reset` — `npm run reset` is the KIT's reset and would replace the instance with
the kit's own sample data. `reset:clean` creates `admin_av`; the other two accounts and every
password are made by hand, and the password prompt is interactive so no secret reaches a command
line. `--person` links the account to a roster row, without which an instructor account cannot be
named on a session at all.

`seed:history` takes about seventy seconds and refreshes the assessor analytics itself when it
finishes. Expect roughly 9 000 sessions, 11 000 records and 536 subjects.

## Proofs after every server deploy

1. `/api/health` reports `env: prod`, the expected release sha, `framework: CBTA 9 / 73`,
   `subjects: N`, `inference: <mode>`.
2. `npm run smoke` from inside the container fetches every route and every subject page.
3. `npm run verify` green, including the neutrality scan.
4. **Sign in through Cloudflare Access and save something** — open a session, or change a template.
   Not a page load: a POST. Until 2026-09-15 every redirect after a POST was built from the server's
   own bind address, so the write succeeded and the browser landed on a dead URL. It is fixed
   (`lib/http.ts`), and this step is how we would know if it ever came back.
5. Run the first three steps of the demo script by hand on `https://avademo.corvanox.com`.

## Server prerequisites (one-time, Phase 4)

- cvx-hel1 has full-disk LUKS and cannot reboot unattended. Do not reboot it for Ava. If a reboot is
  ever needed, it is a separate, human-attended operation on the Corvanox project's terms.
- Create `/opt/ava/{repo,data}`, the deploy key, the `.env` above, and prove the three published
  ports are free (`docs/01_ISOLATION.md`) before the first `up -d`. Every published port binds to
  127.0.0.1: Docker writes its own iptables rules and bypasses the host firewall, so the loopback
  bind — not the firewall — is what keeps them private.
- Cloudflare: one ingress rule, one CNAME, one Access application — hostname-scoped, nothing else.
  The tunnel reaches the app on `127.0.0.1:${APP_PORT}`.

## Rehearsal

The same sequence has been run on the workstation against a second stack (`-p ava-prod`, ports
3200 / 5434 / 3102, volume `ava-prod-db-data`), alongside the development instance and without
touching it. Doing that again after any change to the Dockerfile, the compose files or the build
sequence costs about four minutes and is the only way these instructions stay true.
